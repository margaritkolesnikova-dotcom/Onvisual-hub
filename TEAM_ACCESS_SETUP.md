# ONVISUAL HUB — авторизация сотрудников

Подготовлено: отдельный кабинет \`/team.html\`, роли, панель администратора, приглашения
по email, общий задачник, комментарии, материалы и персональные дедлайны.

## Что уже реализовано

- **Администратор:** все задачи, создание и правка, назначение исполнителей,
  управление ролями и разрешёнными разделами, приглашения по email.
- **Сотрудник:** только назначенные ему задачи. Статус, ссылка на результат,
  комментарий, дедлайны и разрешённые вкладки.
- Сотрудник **не может** менять исполнителя, создавать и удалять задачи,
  просматривать задачи остальных сотрудников или расширять свои права.
- Проверки делаются **в базе данных (RLS)**, а не только через скрытие меню.
- Меню и рабочие блоки определяются личным профилем сотрудника.
- Есть перенос задач из прежнего локального задачника (только по точному
  совпадению имени или email с уже приглашённым исполнителем).

## Подключение (требуется один раз)

1. Создать проект Supabase в нужном аккаунте. Не присылать секретные ключи в чат.
2. Выполнить \`supabase/team-schema.sql\` в Supabase SQL Editor.
3. В Supabase → Authentication → URL Configuration указать
   **Site URL**: \`https://onvisual-hub.vercel.app\`;
   в **Redirect URLs** добавить \`https://onvisual-hub.vercel.app/team.html\`
   (и URL preview при тестировании, если нужен).
4. В Authentication включить вход через email и **запретить
   саморегистрацию** (пользователи создаются только через приглашение).
   Для рассылки приглашений и ссылок доступа должна быть настроена доставка
   писем; учтите ограничения бесплатной почтовой отправки Supabase.
5. Vercel → проект \`onvisual-hub\` → Settings → Environment Variables:
   - \`SUPABASE_URL\` — URL проекта Supabase;
   - \`SUPABASE_ANON_KEY\` — **publishable / anon** key (клиентский);
   - \`SUPABASE_SERVICE_ROLE_KEY\` — **секретный** service role ключ,
     **только на сервере Vercel**;
   - \`TEAM_APP_ORIGIN\` — \`https://onvisual-hub.vercel.app\`.
   Для production окружения обязательны все ключи. После изменения
   переменных — новая сборка Vercel.
6. Создать первого администратора через Supabase Authentication → Users →
   Invite user. Затем выполнить SQL-вставку из **конца**
   \`supabase/team-schema.sql\`, заменив \`admin@example.com\` на
   приглашённый email; ID берётся из \`auth.users\`, не придумывается вручную.
7. Открыть \`https://onvisual-hub.vercel.app/team.html\`, войти по рабочей
   почте администратора и пригласить команду.
8. В \`Команда и доступ\` назначить роли / разрешённые блоки, добавить задачи.
   При необходимости запустить однократный перенос старых локальных задач.

## Рекомендуемые роли

| Роль | Блоки по умолчанию |
| --- | --- |
| Администратор | Все рабочие блоки + права доступа |
| Линейный продюсер | Задачи, календарь, материалы, продакшен, креатив |
| Креативный продюсер | Задачи, календарь, материалы, креатив, продакшен |
| Монтажёр | Задачи, календарь, материалы, продакшен |
| Креатор | Задачи, календарь, материалы, продакшен |
| SMM/контент | Задачи, календарь, материалы, публикации |
| Наблюдатель | Задачи, календарь, материалы |

В каждом блоке сотрудники видят только **свои** задачи и связанные с ними
материалы. Разрешённые блоки можно изменить из панели администратора.

## Перед тем как выдавать доступ

**Критично:** старый \`/index.html\` и репозиторий сейчас публичные;
информация, уже находящаяся в HTML/JavaScript старого HUB, не может быть
защищена одним входом в \`/team.html\`. Новые данные команды защищены RLS,
но старые блоки не стали автоматически приватными.

Для полной защиты всего HUB дополнительно нужно:
- сделать репозиторий приватным и убедиться, что старые публичные копии
  не раскрывают чувствительные сведения;
- вынести конфиденциальные данные из статического HTML/JS в защищённый
  backend и включить проверку прав для них;
- закрыть доступ к старому публичному HUB на уровне сервера либо перенести
  админскую часть за проверяемую авторизацию.

Пока это не сделано, **не считайте старый корневой сайт конфиденциальным**.
Выдавайте сотрудникам только \`/team.html\`, а не ссылку на основной HUB.

## Приёмочное тестирование

- Администратор входит, создаёт задачи для двух разных сотрудников.
- Сотрудник №1 видит только свои задачи и меняет их статус.
- Сотрудник №2 не видит задачи №1 и не может изменить их через API.
- Неавторизованный пользователь не получает список сотрудников и задач.
- Монтажёр не может поменять назначенного исполнителя или разрешения.
- Администратор видит новые статусы и комментарии после перезагрузки.
- Проверить работу на отдельном устройстве и стабильность почтовых ссылок.

## Важно при изменении продакшена

Новая команда добавлена рядом с действующим локальным задачником, без
удаления старых данных из браузера. До переноса локальные задачи и
\`/team.html\` — **две независимые доски**.
